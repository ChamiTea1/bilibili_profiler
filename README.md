# B站弹幕发送者用户画像分析系统

输入视频BV号，深度分析发送弹幕的用户都是什么样的人。

这是一个开源的 B站弹幕数据分析工具，采用 MIT 许可证。**使用前请务必阅读文末[免责声明](#免责声明)。**

## 快速开始

> **环境要求：Python 3.12 或更高版本**。项目使用了 Python 3.12 的嵌套 f-string 语法（PEP 701），
> 3.10 / 3.11 会在 `import report` 时直接 SyntaxError，无法运行。

```bash
git clone https://github.com/ChamiTea1/bilibili_profiler.git
cd bilibili_profiler
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp config.example.py src/config.py     # macOS / Linux / Git Bash
copy config.example.py src\config.py   # Windows cmd / PowerShell

# 然后打开 src/config.py，**只需要改两处**（在文件里搜「替换这里」即可定位）：
#   ①【替换这里①】LLM_API_KEY  大模型 API Key
#      改法：把现有的一对空引号 "" 中间填上你的 Key —— 引号保留，只填内容 → "sk-你的key"
#      不填也能跑：问题弹幕/问题评论判定与 AI 深掘会自动跳过，采集、破解、画像、报告全部可用
#   ②【替换这里②】SUB_URLS     机场订阅链接
#      改法：同样只往那对 "" 中间贴链接，引号保留；多个订阅用英文逗号分隔
#      不填也能跑：不走代理、直连，其余功能完全照常（只是少了换 IP 抗风控的能力）
# 两处都写了逐步填写说明（含 Windows 的 set / $env: 环境变量写法），其余常量不用动。
# 改完可自检（只打印条数与是否已填，不打印链接/Key）：
#   python -c "import sys;sys.path.insert(0,'src');import config;print('订阅条数',len(config.SUB_URLS),'| LLM Key 已填',bool(config.LLM_API_KEY))"

# 分析一个视频（首次运行会打印二维码，用 B站APP 扫码确认）
python run.py BV1vu4y1b7Y9
```

跑完会自动启动本地报告服务并打开浏览器：**http://127.0.0.1:8001**

`python web.py` 可以自己启动报告服务；

换端口用 `python web.py --port 9000`（跨平台，推荐）。

> Windows 注意：`PROFILER_PORT=9000 python web.py` 是 **bash 前置换值语法**，cmd/PowerShell 不支持。
> Windows 下请用 `--port`，或分开两条命令：cmd 用 `set PROFILER_PORT=9000`、
> PowerShell 用 `$env:PROFILER_PORT="9000"`，再执行 `python web.py`。
> 分析时同理：`python run.py <BV号> --port 9000` 会让自动启动的报告页也用该端口。



耗时预期：小视频几分钟，热门视频可能 1 小时以上（受限速硬约束）；**任意时刻 Ctrl+C 可中断，重跑自动续采**。

## 核心特性

- **弹幕采集**：实时弹幕池 + 全量历史弹幕（逐日弹幕池快照，每日上限 1000 条，热门期可能不完整；多分P视频按分P 各采一份），按发送者聚合
- **mid_hash 破解**：MITM（中间相遇）CRC32 秒级反查，覆盖全部 ≤10 位 UID，内存小表无需构建大文件
- **多源明文交叉验证**：评论区（含子评论补采，最多 100 页）+ 充电鸣谢名单 + 互动弹幕 commandDms 获取明文 UID，计算 CRC32 进行匹配；同一 hash 的候选全部保留；明文关联、候选存在性和身份归属分别判定
- **全局证据库**：按 `(hash, UID, 来源, 视频)` 保存明文候选，保留碰撞冲突；纯破解不进入证据库，旧破解记录保留审计并隔离
- **IP 属地画像**：从评论接口提取发送者地域分布
- **刷屏智能检测**：不删除、只标记，区分正常重复与恶意刷屏
- **四维度画像分析**：
  1. 用户主页信息（等级、大会员、硬币数、认证等）
  2. 互动内容足迹（投稿、动态、收藏夹、评论）
  3. 社交关系网络（关注列表、粉丝、互关）
  4. 行为模式分析（活跃时段、活跃周期、消费行为）
- **扫码登录**：B站APP扫码，Cookie自动保存复用（支持自动刷新）
- **交互式Web报告**：`python web.py` 启动本地服务（127.0.0.1:8001），首页视频列表（搜索/排序/分页）+ 九标签页报告（概览/用户画像/弹幕浏览器/问题弹幕榜/争执焦点/问题评论榜/高回复评论/低置信度/纯破解候选，标签页与筛选状态写入URL可分享，@media print 打印样式）；首页与报告页支持一键删除报告/重新生成；run.py 分析完毕自动打开交互式报告，quick_test.py 独立导出并打开采样报告（WEB_AUTOSTART 可关）
- **手动弹幕分析**：Web 弹幕浏览器勾选发送者 → 后台强制分析（UID解析+采集+画像+LLM深掘），进度轮询，失败明细透出可重试，完成自动刷新并恢复现场（标签页/筛选/滚动位置）
- **跨视频足迹**：用户卡片「其他视频足迹」区块展示该用户在其他已分析视频中的出现情况，及他在那些视频里发过的弹幕与评论样本（评论随分析持久化到 comments 表）
- **跨视频重叠用户面板**：首页列出在 ≥2 个已分析视频中都出现过的发送者（点视频条目可展开该用户在其中的弹幕/评论明细样本），用于找跨视频带节奏/水军账号。注意覆盖口径：面板数据源是 senders 表，收录的是**通过兴趣分阈值（中/高刷屏、问题弹幕命中）被解析的用户 + 问题评论直引作者**，不要求画像采集成功（名字缺失时显示 UID）；从未命中阈值的发送者不会被解析，也就不在面板范围内——低强度但跨视频持续出现的潜水账号覆盖不到，这是兴趣分漏斗的固有取舍（弹幕匿名，必须逐视频破解才知道是谁）
- **高回复评论页**：回复数达阈值的评论单独成页（潜在争执热点），按回复数降序展示，附高赞回复样本与「去B站围观」链接
- **用户互动时间线**：`/user/<UID>` 页追踪某个用户在全部已分析视频中的弹幕/评论互动（按最近互动倒序，含样本时间；仅覆盖已分析视频范围）
- **数据导出**：CSV/JSON 导出（report_{BV号}_{时间} 前缀），Web 报告页提供下载链接
- **断点续采**：SQLite持久化，中断后可恢复

## 用法

```bash
# 分析视频
python run.py BV1vu4y1b7Y9

# 强制重新分析（清除该视频全部缓存并强制重采全部用户）
python run.py BV1vu4y1b7Y9 --force

# 限制最大分析用户数
python run.py BV1vu4y1b7Y9 --max-users 50

# 跳过阶段5用户采集的网络请求：只用库内已采数据刷新报告（不发任何采集请求）
# 未采集的用户本轮不出画像，去掉该参数重跑会自动续采，不丢数据
python run.py BV1vu4y1b7Y9 --skip-collect

# 跳过阶段7 LLM 重点深掘：只少 AI 文字画像，判定/画像/报告照常（省 token 与时间）
# 也可在 config.py 里设 LLM_DEEP_ENABLED = False 永久关闭；深掘有缓存，之后开启只补没算过的人
python run.py BV1vu4y1b7Y9 --skip-deep

# 批量分析（逐行读取BV号，忽略空行与 # 注释行）
python run.py --batch videos.txt
```

指定第二个参数可分析命中弹幕的发送者：

```bash
python run.py BV1vu4y1b7Y9 "目标弹幕"
python run.py BV1vu4y1b7Y9 "^目标.*|另一种说法"
python run.py BV1vu4y1b7Y9 "带括号(或句号.)的弹幕" --literal
python run.py BV1vu4y1b7Y9 "目标" --regex --max-users 50 --skip-deep
python run.py BV1vu4y1b7Y9 "目标弹幕" --target-history  # 额外补采历史弹幕
python run.py BV1vu4y1b7Y9 "目标弹幕" --target-pool     # 命中后启用多账号和代理池
```

第二个参数含 `\ . ^ $ * + ? { } [ ] ( ) |` 时自动识别为正则，使用搜索匹配；其余文本按完整弹幕匹配，保留空白、区分大小写。`--literal` 强制原文完整匹配，`--regex` 强制正则搜索。表达式须加引号；无效正则在登录前报错，复杂正则匹配超过 `TARGET_REGEX_TIMEOUT`（默认 30 秒）会终止匹配进程，可简化表达式后重跑。

目标模式默认只登录主号，按分P更新当前弹幕池并复用已有弹幕缓存，不先启动 mihomo、验证全部小号或补采历史。需要扩大历史搜索范围时加 `--target-history`；需要多账号/代理池时加 `--target-pool`，只在命中后建池。

目标模式按命中条数、发送者在该视频的已采弹幕数选人，默认最多 `TARGET_MAX_USERS=1000` 个发送者，`--max-users` 可覆盖。先用本地明文证据和 CRC32 候选解析命中者，缺少证据时按需补元信息；评论搜索**默认无页数上限，找到全部待搜索目标即停**。先翻主评论及接口自带回复预览，仍有目标未找到时才搜索隐藏的楼中楼；不会调用常规全量评论采集、问题评论 LLM 判定或整批保存无关作者正文。只保留目标作者的评论原文、时间、点赞与回复属性，原文和独立游标逐页保存，中断后可续采；身份已确认但没有评论正文时也会搜索。可见评论翻完、风控或接口异常时停止并保留当前结果；发送弹幕者可能没有评论，不能保证每人都能找到。已有目标评论可直接复用。

低置信度及未解析者保留原文，不自动采集画像；碰撞候选评论标注身份待核验。画像参考该发送者在本视频的已采弹幕、已找到评论及其个人行为资料；此模式跳过全视频的问题弹幕/评论 LLM 判定，可用 `--skip-deep` 跳过 AI 深掘、`--skip-collect` 仅复用已采用户资料。目标筛选暂不支持 `--batch`。

候选名片和空间辅助资料在命令行分析阶段准备完成：按限速读取头像、昵称、签名、UID 及账号存在性，再保存投稿、动态、关注的公开首页样本（各最多 20 条）。这些资料用于展示同视频分享、关注该 UP 主、相同长发言等线索及原文链接；兴趣和措辞只说明关联，不直接升级身份分级。完成采集后才生成并打开报告，页面只读已保存快照，不自动补采，也没有采集按钮。失败、风控或验证预算不足时保存明确的缺失/未知状态；空间缓存过期只在下次命令行分析时刷新，已生成报告继续展示保存的样本。旧报告缺少资料时，重跑原分析命令补齐；`--skip-collect` 只复用已有候选资料。

报告独立存档，地址为 `http://127.0.0.1:8001/target/<分析编号>`，分析完成自动打开，也可从首页的「目标弹幕分析」进入。报告包含「筛选概览 / 用户画像 / 命中弹幕 / 目标评论 / 纯破解候选」五页；命中原文支持分页、按发送者查看和带分P的时间跳转，「目标评论」展示搜索途中找到的评论原文，不代表该作者的全部评论。CSV 包括未解析与人数上限外的发送者及已确认作者的评论原文，JSON 保留完整命中、评论、筛选和解析证据，文件前缀为 `target_{BV号}_{分析编号}_`。相同条件重跑更新同一份报告，不同条件各自保留，常规视频画像不被目标画像覆盖。目标模式的 `--force` 重新核验入选发送者、重采其资料，保留共享弹幕/评论采集检查点与已找到的评论；常规模式的 `--force` 也保留独立目标快照，明确删除视频时才一并删除。

匹配范围是当前弹幕池与已有缓存；仅加 `--target-history` 才进行历史网络补采。范围受接口可见性、历史窗口和规模上限影响；报告显示搜索状态与各分P采集覆盖范围，零命中也会保存报告。

目标报告集中在独立列表页 `http://127.0.0.1:8001/targets`，入口在首页搜索框右侧的「目标弹幕分析」按钮，报告中可点「返回目标列表」。仅做目标分析的视频不进入首页普通视频列表，也不提供空的「视频报告」链接。曾做过常规分析的视频保留两个报告入口；旧目标快照自动适用这一规则，无须重跑采集。

首次运行会提示扫码登录，请使用B站APP扫描终端显示的二维码。

`python quick_test.py <BV号> --top N` 会把本轮采样画像导出到 `data/quick_reports/`（HTML、JSON、CSV），自动打开独立采样 HTML；采样弹幕、评论和画像不写入全量采集表或检查点。`WEB_AUTOSTART=False` 可关闭自动打开。

用户基础资料按 UID 共享，视频画像按 `(bvid, uid)` 隔离。启动时自动升级旧库；旧的单视频画像直接迁移，多视频共享画像从各视频弹幕、评论和判定缓存重建。归属不明的旧 AI 文本不再展示，可用 `--skip-collect` 重跑生成。问题评论判定只更新成功批次，失败及截断部分保留旧标注。

升级后请重启已有 Web 服务，使其使用新表和新缓存规则；新的 PID 文件包含脚本路径与启动标识，旧纯数字 PID 文件无法安全核验，需手动关闭旧服务。

目标模式自动打开前会检查目标报告接口；旧服务只有视频接口时会明确提示重启，不再直接打开 404 页面。已保存的目标报告无需重新分析，依次运行 `python web.py --stop --port 8001` 和 `python web.py --port 8001` 后访问原链接即可；其他端口替换为实际端口。

可选小号池（多号并行提速 + 风控时轮换兜底）：
``` bash
python login.py alt1
python login.py alt2
python login.py alt3
...
```
建议配置多个小号，可以显著提高采集速度；

`run.py` 建组合池时自动发现账号；用户深度采集阶段按账号分片并行，每个账号保留独立 Cookie 和限速。实际公网 IP 相同的入口共享请求间隔与冷却，吞吐取决于有效出口数量和目标接口状况。触发风控时保留出口、降速并冷却，串行阶段可换下一账号尝试；代理连接故障才切节点。

可选 IP 池（不配也能正常运行）：

- 配置 `SUB_URLS`（多个订阅以逗号分隔）后，内置 mihomo 为每个账号创建独立本机端口和选择组，重复建池复用绑定；切某个账号的节点会清理其旧连接池，不改其他账号的选择。新增账号可热加载，既有端口保持不变。
- 显式设置 `CLASH_ENABLED=1` 时优先使用外部核心；否则有订阅时优先内置核心，再自动探测本机控制器（9090/9999/9097）。外部共享端口采用静态出口，程序不会切换其全局节点。
- 外部核心已有独立 `listeners` 时，可用 `CLASH_ACCOUNT_ROUTES` JSON 指定每个账号的 `proxy_url` 和 `group`（必须各自独立，并覆盖所有账号）。例如：`{"主号":{"proxy_url":"http://127.0.0.1:17890","group":"profiler-main"},"alt1":{"proxy_url":"http://127.0.0.1:17891","group":"profiler-alt1"}}`。账号名须与登录文件对应；外部配置由用户维护，程序不重写其配置。
- 默认通过 `https://api.ipify.org` 探测实际出口，首次尽量去重、每 1800 秒复查；`PROXY_IP_CHECK_URL` 可替换为自己的纯文本 IP 接口，置空禁用。探测走统一客户端限速，失败不判死节点；未知出口保守共享限速。通用 IP 探测不能证明目标站按同一路径出站，外部独立入口应显式绑定所属选择组。
- 启动日志显示账号数、代理绑定数与实测不同 IP 数；`pool.proxy_status()` 提供请求成功/风控/代理故障/业务异常计数和最近 200 次调用耗时 P95，不含订阅或控制器凭证。主池与分片共享降级、重探状态，故障只影响对应入口。统计与调度在本进程内生效。
- 内置核心按实际时间等待控制器和订阅就绪，默认 `PROXY_CORE_STARTUP_TIMEOUT=60` 秒（不含核心下载和退出清理），每 `PROXY_CORE_STARTUP_LOG_INTERVAL=10` 秒显示等待状态。失败时只输出 DNS、TLS、HTTP 拒绝、订阅格式或监听端口等错误类别，核心原文不打印、不落日志文件。
- 订阅请求默认使用 `SUB_USER_AGENT=clash.meta` 标识，可通过环境变量覆盖；HTTP 400 或格式错误时核对机场面板导出的 Clash/mihomo 订阅链接和客户端要求。

批量模式（`python run.py --batch videos.txt`）逐个视频分析，**不会自动启动 web 服务**（避免逐视频弹浏览器）；跑完自行 `python web.py` 即可在首页看到全部视频。中途 Ctrl+C 只会跳过后续视频，已完成的仍保存在库里。

分析名单怎么定（不加 `--max-users` 时）：

- 进入画像的是**兴趣分命中者**：中/高风险刷屏、或至少 1 条问题弹幕、或问题评论达阈值的作者（凭评论明文 UID 直引）；
- 上限随发送者规模浮动：`max(300, 独立发送者数 × 5%)`，绝对封顶 1000；显式传 `--max-users N` 则以 N 为准；
- 未命中阈值的发送者只留在"未解析"里（报告页会标注"已解析 / 全部发送者"比例）——弹幕匿名，必须逐视频破解才知道是谁。

> ⚠️ `--max-users` 是**按弹幕数降序截断**，而问题评论直引作者的 `danmaku_count=0`、排在最后，用了它这些人会**最先被砍掉**。只想快速试跑可以放心用；想让"问题评论作者"这条线完整进报告就别限制，或给足够大的值。

需要主动登录/换号时：
`python login.py`（主号）、`python login.py alt*`（小号）。

## 断点续采机制

全阶段断点续采：任意位置中断（Ctrl+C/崩溃）后重跑自动续上，无需人工干预——

- **弹幕**：实时池先落库，历史快照逐日增量落库 + 逐日检查点（`phase_state` 表）；中断后重跑从下一个日期续采。多分P 视频各分P 独立检查点（分P 1 沿用原键名，其余为 `…:pN`），互不影响、各自续采。
- **评论**：逐页落库 + 游标检查点；中断后重跑从断点页续翻，已入库评论靠 UNIQUE 约束去重。
- **LLM 判定**：批次级缓存（llm_cache），中断后重跑已完成批次零调用。
- **解析/采集**：senders 逐条落库、users 每人落库，解析按规则版本、证据指纹和有效期复核；基础采集缓存继续复用。
- 重跑时各阶段按库内数据存在性独立跳过（弹幕/评论完整判据：检查点 done=1，或本功能前的旧版完整落库）。
- 同一 UID 被多个弹幕 hash 命中时只采集一次；历史解析失败的发送者会在重跑时自动重试。
- `--force` 会清除该视频的 senders/videos/danmaku/comments/检查点缓存、删除不再被其他视频引用的孤立 users 记录，强制全量重采（拿到最新数据）。

## mid_hash 解析策略

| 证据或状态 | 处理方式 | 置信度 |
|------|----------|--------|
| 评论作者明文 UID | 评论作者本人直引画像，不替匿名弹幕确认身份 | 高 |
| 本视频只有一个明文关联候选 | 评论/充电/互动弹幕/视频信息正向 hash 匹配，未发现 UID 冲突，保留碰撞提示 | 高（交叉验证） |
| 仅其他视频有明文候选 | 保留候选，本视频缺少关联佐证 | 低 |
| MITM 完整范围内唯一已确认存在的 UID | 其余候选均明确 -404，所有核验未过期，仍保留范围外碰撞提示 | 高（存在性排除） |
| 多个有效候选 | 保存完整候选与来源，不自动选最小 UID | 候选歧义 |
| 尚有候选验证未知 | 网络/风控/空名片不当作不存在，下轮续验 | 待验证 |

“高（交叉验证）”表示有本视频明文来源佐证，不表示数学上绝无碰撞；直接评论作者的高置信度来自评论接口明文 UID，两者依据分别展示。仅跨视频关联仍为低；完整数学候选集中仅一个确认存在、其他全部明确不存在且核验有效时，按用户采用的实用分级标为“高（存在性排除）”。多个 UID 冲突或仍有未知不升级。同一 hash 的弹幕条数不提高身份置信度。长 UID 可通过明文正向匹配；CRC32 只有 32 位，无法仅凭 hash 唯一恢复身份。

规则版本更新后解析缓存会重新复核。启动时会核对旧中置信度记录的明文来源、所属视频、正向 CRC32 与候选唯一性，符合条件者同步为高；没有足够证据或已有冲突的旧记录不直接升级，无须为显示分级变化重新采集。旧 CRC32 低分级记录只有在完整数学缓存、唯一存在结论及所有明确阴性缓存均有效时才同步升高，不伪造新版指纹；重跑时一个阴性结论过期就必须复核，不能沿用一天的解析缓存。

解析结论记录规则版本、证据指纹、候选与时间，版本/证据变化立即复核，常规结论默认一天复核。数学候选按算法版本与搜索上限缓存；名片存在结果缓存 7 天，明确 `-404` 缓存 1 小时，未知不缓存。批量名片缺席需单点确认，每轮最多 50 次补验，遇风控整轮停止。

UID 收割刷新以本视频已见评论 ID 判断边界，全局已知 UID 也记录本视频来源。未关联的兴趣 hash 可从未采完整的高回复主楼继续收割 UID：每轮最多 10 页、优先 5 个主楼，同楼连续 3 页无新增目标命中转下一个；断点按主楼保存，全部走现有限速客户端。参数集中在 `config.example.py` 的 `UID_*` 配置，旧本地配置缺少这些项时采用默认值。

“低置信度”页同时列出歧义/待验证条目及候选；这些匿名条目不会自动采集或导出 UID 屏蔽。解析质量将候选分配、歧义、待验证及评论明文作者分开统计，候选分配率不是身份准确率。

“纯破解候选”页紧接常规报告的“低置信度”：只纳入解析时没有评论、充电、互动或元信息等明文来源，且有问题弹幕或高中风险刷屏的匿名发送者，扣除人工误报。目标报告也有同名页，保留本次目标匹配的纯破解记录，并注明匹配本身不等于问题判定。同一 hash 在当前搜索范围内的所有已存候选并列展示，不自动取最小 UID；账号已确认存在与存在性待验证分开标注，明确不存在的账号在折叠区保留。候选以长条名片展示头像、昵称、签名和 UID，整张卡片点击直达空间。命令行阶段按限速补齐并保存名片；仅接口明确 `-404` 才排除。全部其他候选都明确不存在、只剩一个已确认存在者时，回写为搜索范围内唯一候选并标高（存在性排除），随后移出候选页，正常解析结果、画像、原候选及核验审计仍保留；有未知或多名存在则保留待验证/歧义。原候选和每个核验时间保留，阴性缓存 1 小时，不因回写延长；旧错误 UID 撤回，错误画像留审计。空间辅助样本在命令行准备，打开或切换报告页面均不触发候选采集。完成存在性排除的高分级候选在后续分析中按高置信度进入画像流程；未知和歧义不用于 UID 屏蔽，纯破解始终不进入明文证据库。目标报告 CSV/JSON 下载从最新快照生成，包含核验后的 UID。

问题弹幕原文独立存入 `danmaku_problems`，因此无 UID、无画像也能展示；成功判定的内容原子替换，失败批次保留旧证据。旧报告可仅读取与当前视频、内容指纹一致的 LLM 缓存恢复问题原文，打开新页不会调用 B站、LLM 或重新破解。旧解析若没有完整候选记录且数学缓存也不存在，需重跑解析补齐。搜索上限仍为 MITM 覆盖范围，不能声称穷尽所有长 UID。

## 刷屏判定标准

- **高风险**：大量重复内容 + 机器人式规律间隔
- **中风险**：中度重复或疑似机器人
- **低风险**：正常发言

系统**不删除**任何弹幕数据，仅在画像中标记风险等级。

## 注意事项

- B站API有风控限制，请求间隔为基础 0.8–1.6 秒（高风险操作 2–4 秒），区间内随机取时长
- 大会员状态、收藏夹等部分数据需要登录后才能获取完整信息
- 用户关注列表等API可能需要登录态，未登录时可能返回有限数据
- 分析大量用户时耗时较长，程序支持Ctrl+C中断并恢复

## 常见问题（FAQ）

**一定要配 LLM API Key 吗？**
不必。不配置（或留空）时，问题弹幕判定、问题评论判定、AI 深掘三个阶段自动跳过，采集、UID 破解、画像、报告全部照常；报告页对应区块显示为空态。

**第一次运行卡在扫码？**
`run.py` 会同时在终端打印字符码二维码并写出图片 `data/qrcode.png`：用 B站APP → 右上角「扫一扫」→ 扫终端或图片 → 在 APP 点确认。等待上限 3 分钟，超时重跑即可。登录态存 `data/cookie.json`，之后自动复用。

**提示 Cookie 失效 / 又要重新扫码？**
Cookie 里带 `_refresh_token` 时会自动续期；若没有它（或刷新失败）就重新跑 `python login.py` 扫码。小号同理：`python login.py alt1`。

**报告页打不开 / 提示端口被占用？**
换端口：`python web.py --port 9000`（Windows 的 cmd/PowerShell 不支持 `PROFILER_PORT=9000 python web.py` 这种 bash 写法，请用 `--port`；环境变量仍可用，写法见「快速开始」）；停掉占用端口的旧实例：`python web.py --stop --port 9000`（不带 `--port` 则针对 8001；它按 pidfile 校验确实是本项目的 web.py 才动手，不会误杀别的进程）。

**启动时卡在「小号池」那一行不动（几分钟没输出）？**
账号校验后会初始化代理出口。若出现 `[ProxyCore] 核心就绪超时`，先看每 10 秒的等待状态：本机控制器未连通时检查核心启动/监听；控制器可达但没有节点时检查订阅拉取和格式；末尾的脱敏诊断可进一步区分 DNS、TLS 或订阅服务器拒绝访问。内置核心启动默认按实际时间等待 60 秒，超时后尝试外部入口或直连；`0 个代理绑定` 表示本轮没有使用项目配置的 HTTP 代理。

普通环境代理已经在 B站客户端和本机控制器会话中禁用，但系统 **TUN/增强模式**通过路由接管流量，仍可能影响订阅、DNS 和节点连接；可暂时关闭 TUN 后重跑同一命令做对照。内置核心的 `DIRECT` 订阅拉取也无法绕过系统 TUN。若订阅只有通过现有代理才能访问，可显式使用已加载该订阅的外部核心（`CLASH_ENABLED=1`，填写控制器和 HTTP 入口），共享入口不轮换系统选择组。`CLASH_ENABLED=0` 只关闭显式外部配置；只要 `SUB_URLS` 非空，仍会尝试内置核心。核心输出可能含凭证，不要直接复制未经脱敏的原始日志或订阅链接。

已遇到系统 TUN 开启时订阅返回 HTTP 400、关闭后内置核心正常就绪的情况。使用内置多账号 IP 池时，建议保持 TUN 关闭；普通系统 HTTP 代理通常可以保留。如需长期同时使用 TUN，应在系统代理侧配置针对内置核心的绕过规则，再核验每个账号的实际出口；程序不自动修改系统路由。

**为什么这么慢 / 一直在冷却？**
B站接口有风控，请求间隔是硬约束（基础 0.8–1.6 秒，高风险接口 2–4 秒），热门视频必然是小时级。可以：① `--max-users 50` 限制分析人数；② 配小号池（`python login.py alt1`）与 IP 池（`SUB_URLS`）提升吞吐；③ 中途 Ctrl+C，重跑会从检查点续采、不重复已采数据。

**怎么删掉数据？**
单个视频：报告页点「删除报告」（清空该视频的弹幕/评论/画像/导出文件）。全部清空：停掉服务后删除 `data/profiler.db`、`data/reports/`、`data/cookie.json`。所有数据都在本地 `data/` 目录，没有任何云端存储。

**LLM 会把数据发到哪里？**
只发给你配置的模型厂商（默认 DeepSeek，可切 GLM / MiMo）：内容是判定所需的弹幕/评论文本与画像证据字段，不含 Cookie、不含 API Key。不配置则完全不外发。

**能只在本地看、不联网吗？**
采集必须联网（要访问 B站接口）；但报告浏览、导出、离线回归测试都不需要网络，前端依赖（Chart.js / wordcloud2）已本地化到 `static/`。

## 局限性与已知边界

> 本节说明本工具**在设计与数据源上无法突破的边界**。请把分析结论当作**线索**而非证据；判定口径、抽样范围与误差来源都写在这里，避免误用。

### 1. 数据源边界（B站接口语义决定，改代码也突破不了）

- **实时弹幕池不全**：接口只保留最近若干条，更早的弹幕已被顶出池子。
- **历史弹幕 ≠ 全量**：历史接口返回的是"**截至该日的最新 1000 条弹幕池快照**"，不是"当日发送的弹幕"。相邻日快照大量重叠或整体滚动，**热门视频早期的弹幕会被永久丢掉**，逐日遍历只能"逼近"而无法还原。
- **回溯窗口有上限**：最多 24 个月 / 400 天（`HISTORY_MAX_MONTHS` / `HISTORY_MAX_DAYS`），更早的弹幕不在分析范围内；到了天数上限会写 `truncated` 标记（属设计性截断，不是失败）。
- **多分P视频**：历史弹幕按分P 分别采集（B站历史接口按 cid 维度，最多前 `HISTORY_MULTIPAGE_MAX_PAGES` 个分P，可用 `HISTORY_MULTIPAGE_ENABLED=False` 退回只采 P1）；**互动弹幕仍只取第 1P**（其价值在明文 mid，非弹幕量）。分P 之前的报告里其余分P 只有实时池数据，重跑分析可补齐。弹幕的 `time` 是**各分P 内部相对秒数**，所以密度轴按分P 分别建桶，画像样本/时间线/弹幕浏览器都会标出 `P{n}`。
- **评论采不完**：主评论最多 100 页（≈2000 条），每条主评论的楼中楼最多补采 25 页（500 条）；触顶时写 `truncated=1` 而不写 `done`，之后每次重跑都是 0 请求、也不会推进——想采更多需调大 `MAX_COMMENT_PAGES`。
- **问题评论判定会截断**：去重后按点赞降序**只判前 2000 条**（`COMMENT_CRINGE_MAX_ITEMS`），低赞评论不参与判定。
- **用户维度全是采样**：投稿 3 页、动态 5 页、关注 5 页（**他人关注列表接口本身只看得到前 100 人**）、粉丝 2 页、收藏夹内容 20 条。因此"社交关系/兴趣画像"是样本而非全貌。
- **只见当下仍存在的数据**：删稿、删评、隐私设置、已注销账号都拿不到；IP 属地只在评论里（B站已下线主页属地字段）。
- 报告页顶部的"数据边界"提示条与"已解析发送者 / 全部发送者"比例，就是对这些边界的如实标注。

### 2. 匿名身份解析（mid_hash → UID）的数学上限

- MITM CRC32 反查**只覆盖 ≤10 位 UID**；长 UID 可由明文来源正向关联，不能仅凭 32 位 hash 唯一恢复。
- ≤10 位空间下平均约 2.3 个候选/哈希。多个候选同时存在时保留歧义，不取最小 UID；名片存在性只能确认账号存在，不能证明其发送了匿名弹幕。
- 结论：**新注册账号若从未在评论区或充电名单露面，基本解析不出身份**，只会留在"未解析"里。
- **全流程是兴趣分漏斗**：只有中/高刷屏、问题弹幕命中者，以及达阈值的问题评论作者会进入解析与画像名单，其余发送者不解析（跨视频重叠面板同样只覆盖这部分人）。低强度但长期潜水的账号覆盖不到，这是弹幕匿名性的固有代价。

### 3. 判定准确性（启发式 + LLM 双重不确定）

- **刷屏检测是规则启发式**（重复率、相似度、滑动窗口爆发、全池 P95 相对离群、群体复读事件），阈值可调但**必然有误判**；它只标记 `spam_level`，**不删除任何弹幕**。
- **LLM 八类判定受厂商与模型漂移影响**：判定口径带版本号、缓存按模型名隔离；模型可能返回空正文（会自动重试）、被厂商内容审核拦截（该批按空跳过）。
- 口径是**"宁漏勿冤"**，所以**漏报多于误报**；误报可用条目上的「误报」按钮人工纠正（弹幕按**内容全文**粒度——一条标记会连带所有发送同内容的发送者；评论按 rpid）。
- **AI 深度画像只覆盖兴趣分 top K**（默认 20 人，`LLM_DEEP_TOP_K`），其余用户只有规则标签。

### 4. 规模、风控与网络

- 限速是硬约束：请求间隔基础 0.8–1.6 秒、高风险接口 2–4 秒（区间内随机）。**大视频分析是小时级**——实测 560 人规模时，仅用户采集阶段就耗时约 84 分钟。
- 采集人数上限 = max(300, 独立发送者数×5%)，绝对封顶 1000；但**问题评论作者直引不受该上限约束**，名单可能明显超出。
- `--max-users` 是**按弹幕数降序截断**，而问题评论直引作者的 `danmaku_count=0`，会**最先被砍掉**：想保留这条线就不要用 `--max-users`，或给足够大的值。
- **IP 维度是全局单点**：内置核心只有一个 mixed-port、一个 select 组，所有账号共享同一出口 IP，"换号+换 IP"实际只有换号这一维。
- 依赖有效登录 Cookie；cookie 中若没有 `_refresh_token`，过期后只能重新扫码。
- 触发风控会进入冷却（默认 600 秒，单账号池 120 秒），期间采集停滞；代理节点质量直接影响成功率。

### 5. 平台与部署

- Web 报告**只监听 127.0.0.1** 并强校验 Host/Origin，**不能远程访问**（有意设计）；job 状态与页面缓存在内存里，**服务重启即失**。
- Linux 之外能力打折：`--stop` 在 Windows 依赖 PowerShell 查询进程；防孤儿进程的 `PDEATHSIG` **仅在 Linux 生效**，macOS/Windows 下强杀父进程可能留下 mihomo 孤儿进程。
- 数据是本地单文件 SQLite；库变大后报告渲染变慢。导出文件只增不删，需要自行清理 `data/reports/`。

### 6. 隐私与合规

- **LLM 判定与深掘会把弹幕原文、评论原文、昵称/签名/关注摘要等发送给第三方模型厂商**（DeepSeek / 智谱 / MiMo），属真实的数据出境；不配置 `LLM_API_KEY` 时所有 LLM 功能自动跳过，可完全离线运行。
- Cookie 与小号池等同账号登录态（`data/cookie.json`、`data/cookies/*.json`，已在 `.gitignore` 中）；仍建议 `chmod 600` 并加密存储。
- 对他人弹幕/评论做身份画像是个人信息处理行为，**合规责任完全在使用者**，详见下方[免责声明](#免责声明)。

### 7. 工程现状

- 项目**没有单元测试框架**，端到端验证依赖真实网络与有效 Cookie（`quick_test.py` 冒烟 / `run.py` 全流程）。
- 现有离线检查手段：**`python tests/run_all.py`**（484 项离线回归，秒级、无需网络与 Cookie）+ `--lint` 附带 `pyflakes` 静态检查（抓未定义名这类回归）。代理改动可额外运行 `python tests/offline/regress_proxy_pool.py --mihomo`，用已有核心和本机临时 HTTPS 服务验证真实路由，不访问外网。改动后建议再跑一次真实冒烟（`quick_test.py` 或 `run.py`）。

## 贡献

欢迎提交 Issue 和 Pull Request。提交前请：

1. 确保代码风格与现有项目一致（中文注释、中文输出）。
2. 不要提交 `src/config.py`、`data/` 目录或任何含密钥/凭证的文件。

   `python tests/run_all.py --lint`（Ubuntu/Windows × Python 3.12），不通过会标红。
